# Package 3 candidate qualification

The separate `package3-qualification.yml` workflow runs only on `release-qualification/package3-*` branches. It calls ordinary CI with an optional frozen source manifest, then uses the existing protected `RELEASE_SIGNING_KEY` to sign the exact prepared Neptune 0.1.19 Linux and Windows release manifests. It verifies the expected published public-key identity before signing and checks each signature independently with OpenSSL. The workflow has `contents: read`; it creates no Git tags, releases, deployment, or public assets.

The source verifier checks the complete frozen checkout file set and restores the original qualified worktree bytes, including recorded CRLF/LF differences, before compiler/tests run. Empty optional inputs preserve ordinary CI behavior. Passing source CI does not claim a different compiled binary is the locally qualified artifact. The signing request binds the exact prebuilt artifact SHA values; Windows Authenticode changed only the signature envelope around the qualified PE image.

The Windows certificate is owner-selected and self-signed. It is separate from the RSA-PSS manifest key. Default public Windows trust and SmartScreen reputation are not claimed; the certificate must be explicitly trusted in the intended managed environment, and native trust/install/update qualification remains mandatory. No private certificate key is committed.

Native ARM64 is excluded from current package 3 acceptance by explicit owner decision because an appropriate environment is unavailable. That disposition is N/A, not a test PASS or a native ARM64 support claim. The unavailable historical Pluto reader remains a separate owner archival waiver, with old-reader/new-v8 and downgrade compatibility unconfirmed.

Candidate corrections first run the targeted Windows WAL and batch scheduler regressions, then the complete ordinary CI gates. WAL checkpoint cooldown begins after checkpoint I/O and connection disposal finish, so slow storage cannot consume the whole cooldown. Pipeline overlap checks retain all 48 original files, publication, bounded batch sizes and resource/cleanup checks; age-based partial groups and singleton fallback are valid. Separate scheduler tests still exercise full groups of 16.

The signing request can refer to an earlier qualified review artifact set while source corrections are being tested. Its exact hashes qualify only those named bytes. Corrected release binaries require their own build, signatures, affected native checks and final metadata; a green source workflow does not transfer previous native acceptance to a different executable.

The second full Windows run retained two native refusals: an unstable outside-hardlink witness and an uncertain initial coherence cut on the shared hosted system volume. The package 3 workflow now qualifies the unchanged native tests on a separate, disposable NTFS volume with its own USN journal, using the existing `NEPTUNE_FRESH_CYCLE_TEST_ROOT` input. This tests the shared-volume-noise hypothesis; success must be observed, not assumed. Every original hardlink, UNKNOWN, membership, cursor and baseline assertion remains required. The dedicated fixture directory receives its owner SID and SYSTEM permissions at creation, before tests; no shared filesystem ACL is changed. Setup identity, USN logs and native evidence are retained, and only the exact owned VHDX is detached. An empty optional workflow input preserves ordinary CI volume selection. No additional product runtime change is made for this environment qualification.

The initial 8 GiB isolated volume was correctly refused by four batch fixtures with an unchanged 10 GiB free-space floor. The corrected environment has a 24 GiB expandable volume and separately requires 12 GiB of actual backing storage before creation: the 10 GiB floor plus a 2 GiB build/test forecast. Thin virtual capacity is not physical backing evidence. The original 12-pass/4-refusal targeted result remains a failed attempt.
